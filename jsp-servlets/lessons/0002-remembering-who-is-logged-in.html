Explaining Project 5, lesson 2

How the app remembers who is logged in

By the end of this lesson you can explain how Project 5 knows it’s still you on your next click, and the three things it does to keep that safe.

Warm-up from lesson 1

From memory, before anything new. Retrieving last lesson’s ideas a day later is what makes them stick.

Which part of Project 5 decides between showing an error and redirecting to /home?

The servlet is the controller: it decides. UserDao only fetches data, and login.jsp only draws the page.

What does a redirect tell the browser to do?

A redirect is a short response (302 plus a Location header). The browser follows it with a brand-new request. Hold on to that: it is exactly why this lesson is needed.

The problem: HTTP forgets

“The Hypertext Transfer Protocol (HTTP) is by design a stateless protocol.” The first sentence of the Jakarta Servlet specification, chapter 7, “Sessions”.

After a correct password, LoginServlet redirects, and the browser sends a brand-new request: GET /home. Nothing in that request says “this is Ada, who just logged in.” HTTP is stateless: every request arrives on its own, with no memory of the one before.

Yet HomeServlet greets Ada by name. Something must carry “who is this?” from one request to the next. That something is a session.

A ticket and a locker

Cookies exist for exactly this: “Session management: User sign-in status, shopping cart contents…” MDN, “Using HTTP cookies”. The name JSESSIONID is set by the Servlet specification, §7.1.1.

Think of a cloakroom. Tomcat keeps a small locker on the server for each visitor: the session, a Java object of type HttpSession. Each locker has a long random number. Tomcat hands the browser that number as a cookie called JSESSIONID, and the browser shows it on every request after that. Tomcat reads the number and opens the right locker.

Project 5 puts exactly one thing in the locker: the User ID. Two pieces of code do all the work.

The guard and the exit

A filter is code Tomcat runs before the servlet, and it can stop the request there. The flow chart of one request shows both of the app’s filters.

The guard. AuthFilter runs before every request for /home and /photo. It calls currentUserId; if the answer is null, it redirects to /login?required and the servlet never runs.

The exit. Logging out sends POST /logout, and LogoutServlet calls session.invalidate(): the locker is emptied and destroyed. The browser still holds the old ticket, but it now opens nothing. In the test, sending the old cookie to /home after logout got a redirect to /login?required.

The timer. web.xml sets <session-timeout>30</session-timeout>: a session left unused for 30 minutes is destroyed automatically.

The timeout is in minutes: Servlet specification, §7.5.

Three protections an interviewer may ask about

Whoever holds the ticket gets the locker, so the session ID is as valuable as the password. The app protects it in three ways.

A new ticket at login

“The session ID regeneration is mandatory to prevent session fixation attacks.” OWASP Session Management Cheat Sheet. JSPs join a session by default (“Default is true”): Jakarta Pages 4.0, the page directive.

You get a ticket before you log in: every JSP joins a session by default, so just viewing login.jsp creates one. In the test, the first visit got JSESSIONID=71934BB6….

At login, LoginServlet throws that session away and starts a fresh one, which is why the ID above became 4EE2E79B…:

HttpSession old = req.getSession(false);
if (old != null) {
    old.invalidate();
}
req.getSession(true).setAttribute(SESSION_USER, userId);

This stops session fixation: an attacker who planted a known session ID in your browser before you logged in would otherwise be logged in as you the moment you did.

A ticket scripts can’t read and other sites can’t use

HttpOnly: MDN, cookie security. Lax: “the browser only sends the cookie in same-site requests and cross-site top level GET requests.” Tomcat 11, Cookie Processor.

  • HttpOnly, set in web.xml: JavaScript on the page cannot read the cookie, so even a script injected into a page couldn’t steal the ticket.
  • SameSite=Lax, set in META-INF/context.xml: if another website tries to make your browser POST to the app, the browser leaves the ticket out. This is a basic defence against cross-site request forgery (CSRF).

A logout that can’t happen by accident, and leaves nothing behind

GET requests “should only retrieve data”: MDN, HTTP request methods. no-store means “any caches of any kind (private or shared) should not store this response”: MDN, Cache-Control.

  • Logout is a POST. A GET should only read, never change anything. A plain link could be followed by a browser prefetching pages, logging you out without a click. In the test, GET /logout just redirects to /home.
  • Private pages are sent Cache-Control: no-store by AuthFilter, so the browser keeps no copy of your Home page. After logout, Back can’t show it from a stored copy.

Practice

Answer from memory, without scrolling up.

Put one visit, from first page to logout, in order.

Steps

  1. Viewing the login page gives the browser a JSESSIONID
  2. The correct password swaps that session for a new one
  3. LoginServlet stores the User ID in the new session
  4. AuthFilter finds the User ID and lets /home through
  5. POST /logout invalidates the session

Your order

    Ticket, new ticket, fill the locker, check the locker, destroy the locker.

    What does the JSESSIONID cookie contain?

    Only the ticket number travels. The User ID stays in the session on the server, which is why the cookie is worth protecting but reveals nothing by itself.

    Which part checks for a logged-in user before /home runs?

    A filter runs before the servlet. AuthFilter guards /home and /photo, so HomeServlet can assume someone is logged in.

    Why does LoginServlet throw away the old session at login?

    That is the session fixation defence. If the ID survived login, anyone who knew it beforehand would share your logged-in session.

    What does HttpOnly on the session cookie stop?

    Plain HTTP is what the Secure flag addresses (production would add it with HTTPS). Cross-site requests are SameSite’s job. Lifetime is the 30-minute session timeout.

    You log out, then send the old cookie to /home. What happens?

    The ticket survives in the browser, but invalidate() destroyed the locker it pointed to. AuthFilter finds no User ID and redirects to /login?required, which is exactly what the test showed.

    Why is logout a POST form rather than a plain link?

    Logging out changes state on the server, so it must not be a GET that a prefetcher or crawler could trigger. POST is not encrypted (only HTTPS is), and links do send cookies.

    Say it to Ithena

    Start the timer and answer out loud. Then tick off what you covered.

    “How does your app know a user is logged in, and how do you keep that safe?”

    “HTTP is stateless, so I use the servlet session. When the password checks out, LoginServlet throws away any existing session, creates a new one, and stores the User ID in it. Creating a new one prevents session fixation. Tomcat sends the browser a JSESSIONID cookie, and the browser sends it back on every request, so the server can look the session up. AuthFilter runs before /home and /photo: no User ID in the session means a redirect to the login page. The cookie is HttpOnly, so scripts can’t read it, and SameSite=Lax, so other sites can’t post with it. Logout is a POST that invalidates the session, and private pages are sent no-store so Back can’t show them afterwards.”
