Explaining Project 5, lesson 1

What happens when you click Log in

By the end of this lesson you can walk Ithena through a login in five steps, naming the file that handles each one.

Expect Ithena to open with some version of “walk me through what happens when a user logs in.” It is the whole app in one answer: all three technologies in your project title appear in it. This lesson gives you the map. Later lessons zoom in on one stop at a time.

Two messages: a request and a response

The browser–server conversation, step by step: MDN, “An overview of HTTP”.

Browsers and servers talk in HTTP. Every exchange is one request from the browser and one response from the server, and both are plain text. When you press Log in, your browser sends this request:

What each method means: MDN, “HTTP request methods”. How form fields become name=value pairs: MDN, “Sending form data”.

The first line holds the method and the path. GET means “send me this page.” POST means “here is data for you to act on.” The form fields travel in the body as name=value pairs, named after the name attribute of each input in login.jsp.

Your app uses both methods on the same path: GET /login shows the form, and POST /login checks what was typed into it.

The cast

Your project title names three technologies. Each does one job, and Tomcat is the program they all run inside. The colours mark each layer here and in every later lesson.

“A servlet is a Jakarta technology-based web component, managed by a container, that generates dynamic content.” Jakarta Servlet 6.1 specification, §1.1–1.2. A JSP “is translated to create a servlet class”: Jakarta Pages 4.0 specification. Tomcat 11 implements both (Apache Tomcat versions). For JDBC, Oracle’s JDBC tutorial.

  • Browser

    Sends requests and shows the HTML that comes back.

  • Tomcat, the servlet container

    A program that listens for HTTP requests, picks the servlet responsible for each URL, and hands it the request. Project 5 runs on Tomcat 11.

  • Servlet

    A Java class that handles the requests for a URL and builds the response. LoginServlet handles /login. In MVC terms, the controller: it decides what happens.

  • JSP

    An HTML page with placeholders such as ${error}. Tomcat turns each JSP into a servlet behind the scenes, and its only job is to produce HTML. login.jsp is one. In MVC terms, a view.

  • JDBC and the database

    JDBC is Java’s standard way to send SQL to a database and read the results. Only UserDao uses it. The database is H2, and it holds one table, users.

The journey, in five steps

Here is the login request travelling through those layers. Each step is coloured by the layer doing the work.

  1. The browser sends POST /jsp-login/login

    It carries the User ID and password from the form. /jsp-login is the name Tomcat runs the app under; /login is the part your code cares about.

  2. Tomcat hands the request to LoginServlet

    Tomcat knows LoginServlet owns /login because of the annotation above the class. The method is POST, so Tomcat calls doPost. A GET would go to doGet instead.

  3. UserDao fetches the stored password hash

    The servlet asks UserDao for this user’s password hash, and UserDao uses JDBC to run one SQL query against the users table. The database never stores the password itself, only a scrambled version called a hash; lesson 3 explains why.

  4. LoginServlet checks the password and picks a path

    PasswordHasher.verify checks the typed password against the hash. Then one of two things happens:

    Wrong password The servlet puts an error message on the request and forwards to login.jsp, which draws the form again with the message.
    Right password The servlet starts a new session holding the User ID, then redirects the browser to /home.
  5. The browser gets the response

    A forward happens inside Tomcat; the browser never knows. A redirect tells the browser to send a new request. Lesson 3 covers when the app uses each. Your redirect() helper calls sendRedirect, which sends a 302 (Servlet API docs). Background: MDN, “Redirections in HTTP”.

    After a wrong password, the response is the HTML that login.jsp produced. After a right one, it is a short redirect: status 302 and a Location: /jsp-login/home header. The browser immediately sends a new request, GET /jsp-login/home, which HomeServlet answers with home.jsp.

That is the whole app in miniature. Registering, resetting a password, and loading your photo all follow the same shape: request servlet UserDao JSP or redirect. The Project 5 map lists every route, and the flow charts draw them.

Put the steps of a successful login in order.

Steps

  1. The browser sends POST /login with the User ID and password
  2. Tomcat calls the doPost method of LoginServlet
  3. UserDao fetches the stored password hash over JDBC
  4. LoginServlet checks the typed password against the hash
  5. The browser follows the redirect and requests /home

Your order

    Request in, servlet, database, decision, response out. Every route in the app has this shape.

    For the next four, pick the part of Project 5 that does the job.

    Works out which Java class should handle POST /login.

    Tomcat, the servlet container, matches the URL against each servlet’s @WebServlet path, then calls the method that matches the HTTP method.

    Sends SQL to the database to fetch the stored password hash.

    All SQL lives in UserDao. The servlet asks for a hash; it never writes SQL itself. That separation is the point of a DAO (data access object).

    Decides between showing an error and redirecting to /home.

    Deciding what happens next is the controller’s job, and the servlet is the controller.

    Turns the error message into HTML the browser can show.

    The servlet only sets the message; the JSP (the view) decides how it looks on the page.

    Why does Tomcat call doPost rather than doGet when you press Log in?

    login.jsp contains <form method="post" action="${ctx}/login">, so the browser sends a POST. Typing the address /login sends a GET, which runs doGet and shows the empty form.

    In the login request, where are the User ID and password?

    A POST form puts its fields in the body. A GET form would put them in the URL after a ?, which is one reason logins use POST: URLs end up in browser history and server logs.

    After a correct password, what does LoginServlet send back to the browser?

    redirect(req, resp, "/home") sends a 302 with a Location header. The browser then makes a fresh GET /home, and HomeServlet renders home.jsp. Password hashes never leave the server.

    Say it to Ithena

    Now the real skill. Start the timer and answer out loud, as if Ithena were listening. Then tick off what you covered.

    “Walk me through what happens when a user logs in.”

    “When the user submits the login form, the browser sends a POST request to /login with their User ID and password. Tomcat routes it to my LoginServlet, which is mapped to /login with the @WebServlet annotation, and calls its doPost method. The servlet reads the two form fields and asks UserDao for that user’s stored password hash; UserDao runs a parameterised SELECT over JDBC. Then PasswordHasher checks the typed password against the hash. If it doesn’t match, the servlet forwards to login.jsp, which shows the form again with an error. If it does, the servlet starts a fresh session holding the User ID and redirects the browser to /home, where HomeServlet renders the landing page.”
